# 広告実装計画（Android / iOS）

作成日：2026-10-19。現状確認：GitHubをfetch済み。作業ブランチ `codex/ios-native` はリモートと一致し、HEADは `e56f37b`（v1.13.0 / 20）。`main` は旧版 `379aebf` のため、既存のiOS・対局設定の変更を含む作業ブランチを基準とする。

この文書は計画のみ。広告SDKの導入、本番広告の配信、ストア設定の変更はまだ行わない。

## 1. 採用方針

- Google AdMobを第一候補とし、Android・iOSに対応する。
- 参考画像に近い横長カードを作るため、初期案はネイティブ広告。アプリ側は赤・金・生成り色の外枠と配置を用意し、画像・見出し・説明・CTAはSDKから取得した内容を表示する。
- 「広告」とAdChoicesの領域を確保し、配信された素材を含むSDKの正式な広告ビューを使う。SDKにクリック・表示計測を任せる。
- 広告の文言や絵柄を参考画像と同じ内容に固定することはできない。必要な素材の表示条件に従い、無理なトリミング・圧縮・文字の欠落を避ける。最終の高さはテスト広告で決める。
- 初回は各画面1枠。全画面広告・動画視聴の強制・AI解析を広告視聴で解除する仕組みは対象に含めない。
- 実装コストを下げたい場合の代案はアダプティブバナー。特にスクロール内のバナーにはインラインアダプティブを使う。ただしカードの意匠を揃える自由度はネイティブ広告の方が高い。

SDK公式資料：[Androidネイティブ広告](https://developers.google.com/admob/android/native/advanced)、[iOSネイティブ広告](https://developers.google.com/admob/ios/native/advanced)、[スクロール内のバナー](https://developers.google.com/admob/android/banner/inline-adaptive)。

## 2. 画面ごとの配置

| 画面 | 広告の位置 | 守ること |
| --- | --- | --- |
| ホーム | 「過去の棋譜」の下に横長カード1枠 | 設定・各モードのボタンを覆わない。小さい画面は縮小で詰め込まずスクロールで到達させる |
| 対局 | 自分の持ち駒・手番・対局操作の下に1枠 | 盤面と時計を覆わず、盤面を広告分だけ縮小しない。高さが足りない端末は末尾をスクロールで見る |
| 検討 | 評価グラフ・「初期／前へ／次へ／最終／手順」のさらに下に1枠 | 初期表示の盤面・駒・持ち駒・解析・操作の寸法と位置を維持し、下へスクロールすると広告が現れる |
| 過去の棋譜 | 一覧の末尾に1枠（棋譜0件の場合も案内の下） | 棋譜の間へ大量挿入せず、広告を棋譜行として扱わない。件数にも含めない |

広告とアプリのボタンの間に余白を設け、広告の表示完了でボタンが動かないようにする。外枠・素材・AdChoicesを含めて表示領域を確保し、広告自体の上へアプリの装飾やボタンを重ねない。

## 3. 検討モードの寸法維持（最優先）

表示の順序：

```text
後手の持ち駒
現在と同寸法の盤面・駒
先手の持ち駒
形勢・候補手・評価グラフ
初期 / 前へ / 次へ / 最終 / 手順
末尾余白（初期画面内へ広告が入り込まないよう調整）
広告カード ← 下へスクロールして表示
```

- 広告のために画面全体を縮小しない。広告を固定フッターとして画面高から差し引く方法も採らない。
- 広告の上端は「既存コンテンツ末尾」と「初期ビューポート下端」の遅い方より下に置く。背の高い端末でも、初期位置からスクロールして広告を見る仕様にする。
- Androidは現在 `BoardView` のCanvasで描画し、`scale = width / 400` と独自の `studyScroll` を使っている。標準ScrollView内で既存描画領域とSDKの広告ビューを縦に並べる。スクロール用の内容高と、従来の盤面計算に渡すビューポート高を分離する。
- Androidの内部スクロールと外側ScrollViewを二重に動かさないよう、検討中のスクロールは外側へ統一する。スクロール後の駒タップ、長押し、評価グラフの局面移動、広告のクリックをそれぞれ正しいビューへ配送する。
- iOSは既存の `BoardScreen` のScrollView末尾へ `UIViewRepresentable` で広告ビューを追加する。盤面の `aspectRatio(1226/1283)`、最大幅、持ち駒の高さ、解析部の寸法は維持する。
- 広告のロード完了・失敗・再表示で現在のスクロール位置を飛ばさない。広告用の高さ変動は末尾だけに限定する。

アプリID・広告ユニットIDは公開される識別子であり、AdMobログイン情報は実装に不要。支払い情報・ログイン情報をソースへ入れない。

## 5. 広告とアプリの動作

- 広告取得は非同期で行い、AI解析・着手・棋譜読み込みを待たせない。棋譜本文やクリップボードを広告リクエストへ渡さない。
- 広告のない状態、通信失敗、同意の結果広告を要求できない状態でも、対局・検討・棋譜保存はそのまま使える。
- 画面遷移・背景移行・破棄に合わせて広告の取得・表示・リソースを管理し、見えない広告を延々更新しない。再描画や毎手のたびに広告を取得し直さない。
- 対局中は広告をきっかけとした同意ダイアログを突然出さず、初回ホーム等で処理する。広告先への遷移では既存の背景移行と同様に時計・AIの一時停止／復帰を確認する。
- 動画素材を使う場合はSDKの許す範囲でミュート開始とし、棋譜のSEと干渉しないことを確認する。アプリのSE設定だけで広告音声も必ず制御できるとは扱わない。

## 6. 同意・ストア設定

- 起動時にUMPで同意情報を更新し、必要なフォームを表示する。広告要求可否はSDKの判定に従う。設定から必要なプライバシー選択を開けるようにする。[UMP公式資料](https://developers.google.com/admob/android/privacy)
- iOSのATTは広告導入だけで一律に必須とはしない。初期案はIDFAを使わない構成とし、実際のSDK・設定・配信方式でトラッキングが発生しないか確認する。トラッキングを行う方式を選ぶ場合はATT対応と説明文を用意し、拒否されてもアプリを使えるようにする。[iOSプライバシー設定](https://developers.google.com/admob/ios/privacy/strategies)
- 広告SDKを追加すると「棋譜が端末内保存」という説明だけでは広告通信の説明を満たさないため、プライバシーポリシーと両ストアの申告を更新する。対象年齢・配信国と実際のSDK設定に合わせる。[Google Play申告資料](https://developers.google.com/admob/android/privacy/play-data-disclosure)、[App Store申告資料](https://developers.google.com/admob/ios/privacy/data-disclosure)

## 7. ユーザー側で必要な準備

1. **AdMobアカウントの用意**：アカウント登録、本人・支払い・税務情報など、管理画面から要求される手続きを本人が行う。
2. **AndroidとiOSを別々にアプリ登録**：現行Android package / iOS bundle IDは双方 `com.presentsoft.shogi3minutes`。各OSでAdMob App IDを取得し、対応するストア掲載を連携する。
3. **ネイティブ広告ユニットを作る**：OSごとに home / match / study / archive の4枠、合計8ユニットを推奨。提供するのはApp ID 2個と広告ユニットID 8個。ログイン情報の共有は不要。
4. **開発者サイトとapp-ads.txt**：サイトURLとAdMobが表示するapp-ads.txtの行を用意する。こちらで公開用ファイルを作成できる。本人側ではサイトの公開先を決め、ストアの開発者サイト情報を登録する。確認ファイルはドメイン直下の `/app-ads.txt` に置き、AdMobで確認する。アプリの検証・準備審査が通るまで完全な本番配信にならない点を管理画面で確認する。[設定手順](https://support.google.com/admob/answer/9363762)、[アプリの検証](https://support.google.com/admob/answer/14538460)
5. **対象年齢・配信国・プライバシー内容の決定**：子ども向けにするか、どの国へ配信するかを決める。こちらが用意するポリシー・ストア申告案を確認し、AdMobの「プライバシーとメッセージ」で必要なメッセージを設定する。
6. **公開時の確認**：Google Playの「広告あり」とデータセーフティ、App Storeのプライバシー申告を更新する。iOSの実機配布が必要な場合はApple Developerの署名設定も用意する。現在の未署名IPAのビルド成功と、実機配布・本番広告配信は別の完了条件とする。

上記のIDが未準備でも、公式テスト広告IDを使った実装・画面検証・Actionsビルドは先に進められる。

## 8. 進め方と完了条件

1. **基準記録**：広告導入前の同じ端末・向き・画面幅でスクリーンショットと盤面／駒／持ち駒／操作部の矩形を記録する。
2. **テスト広告で実装**：共通の広告管理と4画面の枠、Androidスクロール改修、iOSラッパーを作る。モックでレイアウトを安定して検証し、公式テスト広告でSDK接続も確認する。
3. **回帰・レイアウト検証**：広告なし／ロード中／表示済みで、検討の各寸法とスクロール0の位置が同一であることを座標でも比較。下へスクロールして広告全体へ到達し、戻ると同じ盤面を操作できることを確認する。
4. **操作検証**：広告付近でのスクロールとクリック、盤面タップ、長押し、持ち駒、合法手表示、評価グラフ、手順再生SEを確認。対局の先後・時計・CPU、棋譜保存・復帰も従来どおり動くことを確認する。
5. **失敗系とプライバシー**：オフライン、広告なし、同意拒否、フォームエラー、背景復帰、画面遷移連打でゲーム継続・破棄処理を確認する。小型Android・通常サイズiPhone・iPad等で確認する。
6. **Actions成果物**：Android APK、iOS未署名IPAとSimulator版、ソース、検証結果をGitHubリンクで渡す。実機での広告表示・遷移・音・スクロールも確認する。iOS実機検証には署名済み配布環境が必要。
7. **本番切り替え**：本番ID・app-ads.txt・同意メッセージ・ストア申告・AdMob審査状態を確認した後、本番用ビルドを作る。開発・自動テストは公式テスト広告を使い、本番広告をクリックして動作検証しない。[テスト広告の公式資料](https://developers.google.com/admob/android/test-ads)

本番の広告配信量や収益、AdMobの審査完了時期は、コードのビルド成功では保証しない。
